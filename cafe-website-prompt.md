# Build a static multilingual cafe-restaurant website

Build a static, multilingual website for a cafe-restaurant using Next.js (App Router) with static export. Follow the emil-design-eng philosophy for UI polish, component design, motion, and the small details that make the site feel great.

Work through the **Tasks** section at the bottom in order. Finish and verify each task before starting the next. Ask me before adding any dependency beyond those listed.

## 1. Goal

A fast, mobile-first cafe website with these pages:

- Menu (list)
- Menu item detail (one page per item)
- About us
- Reserve (phone number and text only, no form)

Expected traffic is about 100 users/hour, so everything must be pre-rendered. There is **no runtime server and no runtime database**.

Placeholders to replace before running: cafe name, phone number, address, opening hours, languages (default assumption: `fa` default/RTL and `en`).

---

## 2. Tech stack

- Next.js (latest, App Router), TypeScript
- `output: 'export'`, `images: { unoptimized: true }`, `trailingSlash: true`
- SQLite via `better-sqlite3`, used **only at build time**
- Tailwind CSS (use logical properties such as `ms-*`, `me-*`, `ps-*`, `pe-*`, `text-start` so RTL works without overrides)
- No API routes, middleware, SSR, or server actions (incompatible with static export)

---

## 3. Data layer (SQLite at build time)

- Database file: `data/cafe.db`, committed or generated by a seed script (`scripts/seed.ts`, run via `npm run db:seed`).
- Schema, with translations in separate tables keyed by language:
  - `categories(id, slug, sort_order)`
  - `category_translations(category_id, lang, name)`
  - `menu_items(id, category_id, slug UNIQUE, price, image TEXT NULL, tags, is_available, sort_order)`
    - `slug`: lowercase Latin, shared across languages (e.g. `iced-latte`)
    - `image`: filename in `public/images/menu/`; `NULL` means use the placeholder
  - `menu_item_translations(item_id, lang, name, description, long_description NULL, ingredients NULL, allergens NULL)`
  - `site_content(key, lang, value)` for About page text, hours, address, phone, Reserve page text, optional WhatsApp/Telegram links
- Seed with realistic sample data: 4 categories, about 5 items each, in `fa` and `en`. Every item has a unique slug. Fill the extra fields (`long_description`, `ingredients`, `allergens`) for at least a few items.
- `lib/db.ts`: a single read-only connection and typed query helpers (`getMenu(lang)`, `getContent(lang, keys)`, `getAllItemParams()`). Queries run only during `next build`.
- `better-sqlite3` must never be imported in client components. Only server components and `generateStaticParams` use it.
- **Avoid repeated DB hits during the build.** Memoize reads at module level (for example, load the whole menu once per language into a `Map` and reuse it). Pages read from that cache and do not run a query per page.

---

## 4. i18n

- Languages: `fa` (default, RTL) and `en` (LTR). Keep the language list in one config file (`lib/i18n.ts`) so more can be added easily.
- Do NOT use Next's `i18n` config (unsupported with export). Use an `app/[lang]/` route segment.
- `generateStaticParams()` in `app/[lang]/layout.tsx` returns every language, so each language is pre-built once at build time.
- UI strings (nav, buttons, labels) live in `dictionaries/fa.json` and `dictionaries/en.json`.
- Set `<html lang dir>` per language in the `[lang]` layout.
- `params` is a Promise in current Next.js. Always `await` it.
- Root `app/page.tsx`: a tiny client-side redirect that reads `navigator.language` and goes to `/fa/` or `/en/`, with `fa` as fallback. Add a `<noscript>` link too.
- Language switcher in the header that keeps the user on the equivalent page (including the same item slug) in the other language.
- `generateMetadata` per page and language: title, description, canonical URL, and `hreflang` alternates.
- Format prices with `Intl.NumberFormat` per locale (Persian digits for `fa`).

---

## 5. Pages

1. **Home** (`app/[lang]/page.tsx`): short intro with a link to the menu (or redirect to the menu).
2. **Menu** (`app/[lang]/menu/page.tsx`): sticky, horizontally scrollable category navigation on mobile. Items show name, description, price, optional image, dietary tags. Each item card links to its detail page. The whole card is the tap target (44px minimum), with press and hover states. Keep it scannable and fast.
3. **About us** (`app/[lang]/about/page.tsx`): story, opening hours, address, map link (external link or lightweight lazy-loaded embed), contact info. All content from `site_content`. Add JSON-LD `Restaurant` structured data.
4. **Reserve** (`app/[lang]/reserve/page.tsx`): NO form and NO backend. Short text, a large obvious tap-to-call button (`tel:` link), and opening hours. Optionally show WhatsApp/Telegram links if configured in `site_content`.

Each page uses `generateStaticParams` so DB work happens once per language at build time, never per request.

---

## 6. Menu item detail pages

Every menu item gets its own statically generated page in each language: `/fa/menu/<slug>/` and `/en/menu/<slug>/`.

- Route: `app/[lang]/menu/[slug]/page.tsx`
- `generateStaticParams()` returns every `{ lang, slug }` combination from ONE query (`getAllItemParams()`). Only items with `is_available = 1` are included.
- `export const dynamicParams = false` so unknown slugs 404 and nothing renders at request time.
- Page content:
  - Large image (via `getImageSrc` with placeholder fallback), name, full description, price, dietary tags, category link
  - Optional `long_description`, `ingredients`, `allergens`
  - "Back to menu" link with an RTL-aware arrow icon
  - Previous/next item links within the same category (hidden at the ends)
  - "Reserve a table" call-to-action linking to the Reserve page
- `generateMetadata` per item and language: title (`<item> | <cafe>`), description from the item text, Open Graph image, canonical URL, `hreflang` alternates.
- JSON-LD `MenuItem` structured data (name, description, price, image).
- Subtle shared-element-style transition from list to detail only if it can be done cleanly. Respect `prefers-reduced-motion`.
- All item URLs in every language are included in `sitemap.xml`.

---

## 7. Images and placeholders

No real photos exist yet, so every image must work with a placeholder and be swappable later without code changes.

- Create `public/images/placeholders/` with locally generated SVG placeholders. Do NOT use external services (such as placehold.co); the site must work offline and stay fast:
  - `menu-item.svg`: neutral, warm-toned card with a simple cup/plate icon
  - `hero.svg` and `about.svg`: wide placeholders for the home/about pages
- `lib/images.ts` with `getImageSrc(image: string | null, kind: 'item' | 'hero' | 'about')`. Returns the real path if the file exists at build time (`fs.existsSync`), otherwise the matching placeholder. A missing file must never cause a broken image.
- In seed data, leave `menu_items.image` as `NULL` for most items and set 1 or 2 to real filenames to demonstrate the fallback.
- Optionally generate a tiny blur-style placeholder (solid color or low-res data URI) per image.
- Every `<img>` has explicit `width` and `height` (or a fixed `aspect-ratio`), `loading="lazy"` (except the first visible image), and meaningful `alt` text from translations (empty `alt=""` for purely decorative placeholders).
- Placeholder colors come from the design tokens and respect dark mode.
- README: drop real images into `public/images/menu/`, set the filename in the DB or seed file, rebuild. Recommend WebP at about 800px wide, under 100 KB each.

## 8. Design and polish (apply emil-design-eng and the skills in section 0)

Use `/emil-design-eng` as the base, `/animate` for building motion, `/apple-design` for physical, interruptible interactions, and `/review-animations` to check the result.

- Pick a distinctive, warm visual identity that fits a cafe. Avoid generic templated looks.
- Careful typography: Vazirmatn for Persian, a complementary Latin font for English, loaded with `next/font`, only needed weights.
- Considered micro-interactions: press and hover states, subtle transitions with proper easing and short durations, nothing gratuitous. Respect `prefers-reduced-motion`.
- Sticky header and category nav that feel smooth, with 44px minimum touch targets and a proper `:focus-visible` style.
- Details: consistent spacing scale, balanced line heights per script, correct RTL mirroring of icons and arrows, no layout shift.
- Dark mode via `prefers-color-scheme` if it can be done cleanly.

## 9. Performance, SEO, accessibility

- Target Lighthouse 95+ on mobile. Pages under about 1 MB. Images in WebP, lazy loaded, explicit dimensions.
- Semantic HTML, accessible labels, good contrast, keyboard navigable.
### Sitemap (generated dynamically from the DB at build time)
- Use `app/sitemap.ts` (Next.js metadata route) with `export const dynamic = 'force-static'` so it is emitted as a static `out/sitemap.xml` during `next build`.
- Do not hardcode URLs. Build the list from the same cached data layer used by the pages:
  - every language home page, `/menu/`, `/about/`, `/reserve/`
  - every available menu item, in every language, using `getAllItemParams()`
- Each entry has an absolute URL (base URL from `NEXT_PUBLIC_SITE_URL`, with a clear build error if it is missing), `lastModified` (use the DB file's modified time or a `updated_at` column), and `alternates.languages` with the `hreflang` URL for each language.
- Adding an item to the DB and rebuilding must automatically add its URLs to the sitemap.
- `app/robots.ts` (also `force-static`) allows all and points to the sitemap URL.

### Open Graph image for the main page
- Add `app/[lang]/opengraph-image.tsx` using `ImageResponse` (from `next/og`), with `export const dynamic = 'force-static'` and `generateStaticParams` returning every language, so one 1200x630 PNG per language is generated at build time. It is used by the home page and as the default for other pages.
- Design: warm cafe branding, cafe name, short tagline from `site_content` for that language, the logo or an icon. Use design tokens colors. Text direction must be correct for `fa` (RTL).
- `ImageResponse` needs the font loaded explicitly. Load Vazirmatn (Persian) and the Latin font from local files in `public/fonts/` or `assets/` using `fs.readFile` at build time. Do not fetch fonts from the network.
- Add `alt` text for the image (`export const alt`), `size` and `contentType` exports.
- Add `metadataBase` in the root layout and complete `openGraph` and `twitter` (`summary_large_image`) metadata in `generateMetadata` for the home page, with `locale` and `alternateLocale` per language.
- Menu item pages use the item's image as their OG image when a real one exists, otherwise fall back to the language's default OG image.
- Fallback if `ImageResponse` fails under static export: ship a hand-made `public/og/og-fa.png` and `public/og/og-en.png` and reference them in metadata. Tell me if you had to do this.
